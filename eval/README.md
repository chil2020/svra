# Eval 集（Future Work，等 LLM 層完成後才用得到）

這一層要解決的問題只有一個：**prompt 改了之後，怎麼知道是變好還是變壞。**

沒有 eval 的話，prompt 迭代只能靠感覺——改完隨手試兩句覺得不錯就上，
下次再改把前面修好的 case 弄壞了也不會發現。
有一組固定的案例才有回歸測試可依，跟寫單元測試是同一件事。

## 案例格式（`cases.jsonl`，一行一案例）

```json
{"id": "todo-001", "input": "口語轉錄文字", "expected": {"category": "待辦|想法|行程", "fields": {"time": "...", "people": ["..."], "tags": ["..."]}}}
```

`cases.jsonl` 目前只有 3 條，用途是示意格式。

正式的案例要從真實的語音輸入累積——**真實口語的雜訊（贅字、自我修正、講到一半跳題）
才是 eval 有價值的原因**。自己編的漂亮句子測不出模型會在哪裡失敗。

## Runner（尚未實作）

- 逐案例呼叫抽取端點，比對 `category` 是否完全一致、`fields` 逐鍵比對
- 時間類欄位要先正規化再比對（「下週二早上十點」得先解析成實際日期）
- 輸出總準確率與錯誤案例明細，結果存成 `runs/<日期>-<prompt版本>.json`
- 累積一張「prompt 版本 vs 準確率」的對照表，讓每次修改都有依據

## 為什麼排在佇列層後面

抽取端點還沒做，現在沒有東西可以測。
先把 webhook → 佇列 → 轉錄這條路打通，有了轉錄文字才有 eval 的輸入。
