# Eval 集

這裡有兩組，量的是管線的兩層：

| | 案例檔 | Runner | 量什麼 |
|---|---|---|---|
| **抽取層** | `cases.jsonl` | `core/.../ExtractionEvalTest.java` | prompt 改了之後，分類／日期／關鍵字對不對 |
| **ASR 層** | `asr-cases.jsonl` | `whisper-worker/eval_asr.py` | 換模型或換後端之後，CER／專有名詞／速度 |

下半部是 ASR 那組的說明，先講抽取層。

---

## 抽取層

這一層要解決的問題只有一個：**prompt 改了之後，怎麼知道是變好還是變壞。**

沒有 eval 的話，prompt 迭代只能靠感覺——改完隨手試兩句覺得不錯就上，
下次再改把前面修好的 case 弄壞了也不會發現。
有一組固定的案例才有回歸測試可依，跟寫單元測試是同一件事。

## 怎麼跑

```bash
cd core && mvn test -Peval
```

**不在 `mvn test` 裡跑**：它呼叫真的 LLM，慢、不具決定性，結果是各維度的準確率
而不是通過／失敗。混進單元測試裡只會讓平常的建置變慢又變得不可靠。

## 案例格式（`cases.jsonl`，一行一案例）

```json
{"id": "multi-001", "note": "一段話三件事，要拆成三筆", "today": "2026-08-14",
 "input": "明天早上要出發去阿里山，記得先去繳電費，然後想到履歷可以用佇列深度當指標",
 "expected": {"itemCount": 3, "items": [
   {"category": "SCHEDULE", "occursAt": "2026-08-15T09:00", "mustMention": ["阿里山"]},
   {"category": "TODO", "mustMention": ["電費"]},
   {"category": "IDEA", "mustMention": ["佇列深度"]}]}}
```

格式跟最初的草稿有三處不同，都是實作出來之後才知道的：

| 草稿 | 現在 | 為什麼 |
|---|---|---|
| 一個案例一個項目 | `items` 是陣列 | 真實口語一段話常有多件事，「會不會併成一筆」正是要測的 |
| `category: "行程"` | `SCHEDULE` | 對齊實際的 enum，不要多一層翻譯 |
| `time: "下週二 10:00"` | `occursAt` ＋ `today` | 相對日期要能驗算。固定 `today` 才有決定性 |

**不做逐字比對**：同一段話有多種合理的整理方式，逐字比對只會逼人去對齊模型的
表達習慣。量的是可觀察的性質——數量、分類、日期、必須提到的關鍵字、
標題不該混入的口語雜訊。

正式的案例要從真實的語音輸入累積——**真實口語的雜訊（贅字、自我修正、講到一半跳題）
才是 eval 有價值的原因**。自己編的漂亮句子測不出模型會在哪裡失敗。
目前 8 題，其中 `multi-002` 是真實逐字稿。

## prompt 迭代紀錄

| prompt | 通過率 | 改了什麼 |
|---|---|---|
| v1 | 6/8 | — |
| v2 | 6/8 | 加規則「明確日期直接用」＋告知今天星期幾 —— **沒有改善** |
| v3 | 8/8 | 改成給 14 天的日期對照表 |
| v4 | 7/8 | 基準日改為錄音時刻——**日曆表讓模型更愛指派時間，想法類被硬填日期** |
| v5 | 8/8 | 加一條：有日曆表不代表每筆都要有時間，IDEA 沒說時間就是 null |
| **v6** | **8/8** | title 不要寫日期——顯示時會另外排版，寫兩次只是重複 |
| **v7** | **8/8** | occursAt 在 schema 裡改成選填。**prompt 那段字串一個字沒動** |

**v2 沒有改善，v3 才有；v4 還退步了一題。**v3 的關鍵是一個判斷：

> 不要叫模型算日曆，直接給它日曆。

v2 告訴它「今天是星期五」，但它還要自己推「8/17 是星期幾」——而那一步會錯。
v3 把推算變成查表。**這種「加規則沒用、換做法才有用」的差別，沒有 eval 量不出來。**

而 v4 的退步是另一種：**修好一件事會弄壞另一件。**日曆表解決了星期推算，卻讓模型
更傾向替每一筆指派時間，把原本正確的 null 填掉了。這正是回歸測試存在的理由——
沒有它，v4 上線後只會有人抱怨「想法怎麼都跑到行事曆去了」，而沒人知道是哪次改動造成的。

### v7：prompt 沒改，但 prompt 變了

v7 動的不是上面那段字串，是 `ExtractedNote` 這個 record——Spring AI 會從它產生
JSON Schema **接在 prompt 後面**送給模型，還附一句「不得偏離」。
所以型別宣告是**半份 prompt**，而它預設把每個欄位都列進 `required`。

那半份一直在跟手寫的規則打架：規則說「想法沒說時間就是 null」，schema 說 `occursAt` 必填。
v5 就是為了打贏這一仗才加的那條規則（見上面 v4 的退步）。v7 的作法是直接改結構：
標 `@JsonProperty(required = false)`，讓「沒有時間」在型別上就是合法的。

**升版本號是必要的，不只是禮貌**：快取鍵含 `PROMPT_VERSION`（見
`ExtractionCacheKeyGenerator`），不升的話改完 schema 也會拿到舊結果，
比出來的數字是假的。**而快取鍵看不見 record 的形狀——這是要人記得的事。**

#### 順手放寬其他欄位，量出來是退步

原本打算把 `occursAt`、`detail`、`tags` 三個一起放寬，理由是它們的註解都寫著
「沒有就 null」。量完之後只留了第一個：

| 組態 | 重跑 | 通過率 | multi-002 |
|---|---|---|---|
| v6：三個都必填 | 2 次 | 8/8 | 4 筆，23 秒 |
| 只有 `occursAt` 選填 | 3 次 | **8/8** | 4 筆，23 秒 |
| `occursAt` ＋ `detail` 選填 | 2 次 | 7/8 | **8 筆**，46 秒 |
| 三個都選填 | 3 次 | 7/8 | **8 筆**，42 秒 |

`detail` 一放寬，三天行程的真實逐字稿就從 4 筆被切成 8 筆——每天再拆成出發、
住宿、停車、夜市。推測的機制是：**`detail` 必填時，每多切一筆就得多寫一段補充，
那個成本會逼模型把同一天的事併在一起**；放寬之後切分變得沒有代價。

**一個跟「要切幾筆」看起來毫無關係的欄位，決定了切分的粒度。** 沒有 eval 的話，
這個改動會直接上線，然後某天有人覺得「清單怎麼變得好碎」，而沒有人知道是哪一次改的。

每組都重跑 2～3 次而不是跑一次就下結論：模型有隨機性，而**單次結果分不出
「改壞了」和「這次剛好」**。重跑之間要清掉 Redis 的那一版快取，
否則第二次是在重讀第一次的答案。

### 第一次跑同時抓到 eval 自己的兩個 bug

- **時鐘寫死**：`NoteExtractor` 用 `LocalDate.now()`，案例裡的 `today` 根本沒生效，
  相對日期的預期答案每天都會腐爛。改成把「錄音時刻」當參數傳進去。
- **案例自相矛盾**：`multi-002` 的逐字稿說「今天8月15號」，`today` 卻設成 8/14。
  輸入自己打架，模型怎麼選都有話說。

## Runner

`core/src/test/java/io/svra/extract/ExtractionEvalTest.java`，標了 `@Tag("eval")`。

除了逐案例的檢查，**每個案例都會多跑一次跨欄位一致性檢查**：`detail` 裡若寫了
「N月N日」，就要跟 `occursAt` 同一天。這是 `validate()` 抓不到的那類錯誤——
格式合法、日期也在合理範圍，但兩個欄位互相矛盾。實測第一次跑就是它抓到的。

尚未做：把結果存成 `runs/<日期>-<prompt版本>.json`，累積一張
「prompt 版本 vs 準確率」的對照表。目前只印在終端機。

## 為什麼沒有斷言

Runner 跑完只印分數表，不 assert。因為「幾分算通過」取決於當下的目標——
剛換模型時 70% 可能是好消息，穩定之後 90% 可能是退步。
要當成 CI 閘門時再依當時的標準加門檻，而不是先射箭再畫靶。

# ASR 層的 eval

## 為什麼補這一組

決策 13 換掉 ASR 模型的依據是：**一段錄音、兩個詞（奮起湖、KKday）、肉眼比對**。
結論是對的，但那個方法不能重跑，也答不出「換 Breeze-ASR-26 會不會更好」
這種問題。

而 README 自己就寫著這句話：

> 抽取層的 eval 是 8/8，但實際用起來還是有錯——**錯在上游**。

下游有 8 題 eval 與 v1→v6 的迭代紀錄，上游一題都沒有。**最需要被量的那一層
反而沒有尺。**

## 怎麼跑

```bash
# 產出待校對草稿（先用現有模型轉一遍，人只要改錯字，不用從零聽打）
docker compose exec -T whisper-worker python -u eval_asr.py draft > eval/asr-cases.jsonl

# 評分
docker compose exec -T whisper-worker python -u eval_asr.py score

# 換後端／換模型比較（同一把尺）
python -u eval_asr.py score --backend mlx --model BRlin/Breeze-ASR-25-mlx-fp16
```

**Runner 放在 `whisper-worker/` 而不是 core**：ASR 跑在 Python 這一側，
要在 Java 那邊評分就得繞一趟 RabbitMQ，把「量模型準不準」變成
「量整條管線通不通」——兩件不同的事。決策 5 說語言邊界就是服務邊界，
eval 也在同一條邊界上。

## 案例格式（`asr-cases.jsonl`）

```json
{"id": "trip-001", "audio": "627242078597808283.m4a", "verified": true,
 "note": "70 秒連續獨白、有背景音、中英夾雜＋大量台灣地名",
 "reference": "人工校對過的正確逐字稿",
 "mustContain": ["嘉義", "阿里山", "KKday", "QR code", "奮起湖"]}
```

`verified` 是一道閘門。`draft` 產出的 `reference` 就是**模型自己的輸出**，
拿它當標準答案去評分，CER 會是漂亮的 0%——而那個 0% 什麼都沒證明，
它只證明了模型跟自己一致。**一個會給出假綠燈的量尺比沒有量尺更危險**，
所以未校對的案例預設會讓評分直接中止。

## 三個指標，各自回答不同的問題

| 指標 | 回答什麼 | 為什麼不能只看它 |
|---|---|---|
| **CER** | 整體聽得準不準 | 是平均值，會稀釋掉少數關鍵字元 |
| **專有名詞命中率** | 那句話真正的資訊有沒有保住 | 只看它會漏掉整體品質的退步 |
| **RTF / 空輸出率** | 代價是多少 | 準確率不是唯一的軸；空輸出是靜默失敗 |

**為什麼一定要有專有名詞這一欄**：「奮起湖」轉成「正啟湖」在一段 200 字的
逐字稿裡只貢獻約 1% 的 CER，但那則筆記的價值幾乎全在那三個字——
地點錯了，行程就是廢的。決策 13 換模型的真正理由是這個，不是整體 CER。
只看 CER 的話，那次換模型會顯得沒什麼道理。

## 逐字 vs 語意：reference 寫的是「說了什麼」，不是「想說什麼」

校對第一則案例就撞到這個問題：錄音的人自己講錯了——順序顛倒、名稱說得含糊。
那 `reference` 該寫他**實際說出口的**，還是他**想表達的**？

**規則：寫實際說出口的。**

ASR 的職責是把聲音變成文字，不是猜使用者的意圖。參考稿若寫成「想說的」，
那 CER 量到的就變成「模型有沒有幫我修正我自己的口誤」——那是下游抽取層的事
（決策 10 的 prompt 明寫著「明顯是轉錄錯誤的專有名詞，若能從上下文判斷就修正」），
不該記在 ASR 頭上。混在一起量，兩層的責任就都說不清楚了。

`mustContain` 也跟著這條規則：**只放真的說出口的詞**。
說話的人根本沒講清楚的名稱，任何模型都轉不出來，
放進去只會讓分數變成一個永遠達不到的目標，而不是一把尺。

（代價是校對比較累——要照著錄音一字一句聽，不能憑記憶寫。
但一份「憑記憶寫的正確答案」量出來的東西，本來也不能拿來做決定。）

## 正規化：這幾行決定了分數的意義

CER 的數字完全取決於比較前做了什麼正規化，所以每一條都要說得出理由：

| 做什麼 | 為什麼 |
|---|---|
| 去掉所有標點與空白 | Whisper 自己會加標點，而人工校對稿的標點習慣不可能一致。算進去等於在量標點習慣的差異 |
| 全形英數 → 半形 | `ＫＫｄａｙ` 與 `KKday` 是同一個東西 |
| 英文一律小寫 | 大小寫不是聽出來的 |
| **中文字元不做任何轉換** | 簡繁與異體字的差異**是**辨識錯誤，這個專案的輸出就該是繁體 |

改這幾行等於改量尺，舊分數就不能再拿來跟新分數比。

## 量尺自己有測試

`whisper-worker/scripts/test_eval_asr.py`，CI 會跑。

一個算錯的 eval 產出的是**有自信的錯誤數字**——那比沒有數字更危險，
因為沒有人會去質疑一個看起來很篤定的表格。

## 為什麼一樣沒有斷言

理由同抽取層：「幾分算通過」取決於當下的目標。剛換後端時 CER 略升但快三倍
可能是划算的，穩定之後同樣的數字就是退步。要當閘門時再依當時的標準訂。


## 第一次跑出來的基準線（2026-08-19）

模型 `Breeze-ASR-25`，6 個真實語音案例，共 150 秒。

| 案例 | 長度 | CER | 專有名詞 | RTF |
|---|---:|---:|---:|---:|
| idea-001（想法獨白） | 46.4s | **0.0%** | 2/2 | 0.41 |
| trip-001（旅遊行程） | 70.2s | 2.1% | **6/9** | 0.42 |
| escape-002 | 11.4s | 7.1% | 2/3 | 0.50 |
| place-001 | 9.8s | 12.5% | **0/2** | 0.57 |
| escape-001 | 9.1s | 27.3% | 2/3 | 0.60 |
| short-001 | 3.2s | **33.3%** | **0/2** | 1.42 |
| **合計** | **150s** | **4.43%**（加權）<br>**13.73%**（等重） | **12/21（57%）** | **0.47** |

### 三件事只有量了才知道

**一、兩個 CER 差了三倍，那個落差本身就是結論。** 加權 4.43%、等重 13.73%。
`idea-001` 那則 46 秒的日常獨白拿了 0% —— 贅字、自我修正、講到一半跳題全部轉對——
把加權平均整個拉漂亮了。而這個服務的輸入大多是短句，**等重那個數字才貼近體感**。

**二、「4% 錯誤率」會讓人做出錯誤的決定。** 專有名詞命中率只有 57%。
最誇張的是 `trip-001`：**CER 只有 2.1%，但飯店名（蘭桂坊）、住宿（神木賓館）、
林鐵三個都錯了**——那是一則旅遊行程筆記，錯的正好是它唯一有用的資訊。
只看 CER 的話，這則會被判定為「幾乎完美」。

**三、失敗模式非常集中。** Breeze-ASR-25 的日常華語幾乎無懈可擊，
錯的全部是**台灣專有名詞與短句**。這對決策 13 是個修正：換 Breeze 是對的，
但**剩下的問題正好就是 Breeze 本來該解決的那一類詞**。

## 模型比較：同一把尺，三個模型

同一批 6 個音檔、同一組正規化規則、同一個後端（ct2/int8）。

| 模型 | CER（加權） | CER（等重） | 專有名詞 | RTF |
|---|---:|---:|---:|---:|
| **Breeze-ASR-25** | **4.43%** | **13.73%** | 12/21（57%） | 0.47 |
| Breeze-ASR-26 | 11.62% | 16.89% | **13/21（62%）** | 0.45 |
| whisper large-v3-turbo | 12.36% | 15.32% | 9/21（43%） | **0.27** |

### 結論：維持 Breeze-ASR-25

CER 幾乎是另外兩個的三分之一，而它換來的代價只是比 turbo 慢 1.7 倍——
以「轉錄本來就是非同步」的前提（決策 13），那個速度差沒有價值。

### 但 Breeze-26 不是「比較差」，是**換了一組錯誤**

這是只看總分會看漏的地方。同一則 `trip-001`，兩個模型都是 6/9，
但漏掉的**不是同一組詞**：

| | 轉對了 | 漏掉了 |
|---|---|---|
| ASR-25 | KKday、QR code、奮起湖 | 蘭桂坊、神木賓館、林鐵 |
| ASR-26 | 蘭桂坊、神木賓館、QR code | KKday、林鐵、奮起湖 |

**ASR-26 把中文專有名詞救回來了，代價是中英夾雜退步。**
它多吃了一萬小時台語語料，方向就往中文那側偏——而這個服務的輸入
剛好兩種都有。`short-001` 也是：ASR-26 轉對了「面試」（25 轉成「麵室」），
但「保哥」還是錯。

所以「26 比 25 差」這個說法是錯的，正確的說法是
**26 在中文專有名詞上較強、在中英夾雜上較弱，而整體 CER 25 明顯較好**。
只有把兩個指標分開看才講得出這句話。

### 三個模型都錯的那幾個詞，才是真正的訊號

`密室逃脫`、`裕隆城`、`大遠百`——**沒有任何一個模型轉對**。

這代表換模型解決不了它們。這一類「本地商場、常用活動名稱」需要的是
另一種手段：Whisper 的 `initial_prompt` 可以塞入詞彙提示，
或在轉錄後做一層對照表修正。**eval 的價值不只是選模型，
更是指出「這個問題不在模型選擇這一層」。**

## 後端比較：MLX 量過了，不能用

決策 15 說 Ollama 留在宿主機是因為「容器裡吃不到 Metal」。同一句話對
whisper-worker 一字不改地成立——而且更嚴重：CTranslate2 的 Apple 加速是
Accelerate（CPU/AMX）不是 Metal，跑在 Docker 的 Linux VM 裡連那個都吃不到。
所以「把 worker 搬到宿主機用 MLX」看起來是明顯的優化。

**量出來的結果是不能用：**

| | ct2/int8（容器） | mlx/fp16（宿主機 GPU） |
|---|---:|---:|
| 整體 CER（加權） | **4.43%** | 73.25% |
| 平均 CER（等重） | **13.73%** | 298.82% |
| 專有名詞命中 | **12/21** | 10/21 |
| 整體 RTF | 0.47 | **0.33** |

（MLX 那欄是它的**最佳**表現。開啟預設的 temperature 退避之後更糟：
CER 320%、RTF 1.54——退避一直在觸發，每次重解都更亂。）

**症狀不是「慢」也不是「Metal 沒用」**：GPU 加速是真的，長音檔 RTF 0.30 確實
勝過 CT2 的 0.42，幾個專有名詞（裕隆城）甚至比 CT2 準。問題是
**音檔結束之後它會繼續往補滿 30 秒視窗的那段靜音解下去**，接一長串幻覺。
`short-001` 那則 3.2 秒的音檔，CER 是 1175%。

試過而無效的：`chunk_duration`（預設 1.0 會把音檔切碎，改 30.0 好很多但沒解決）、
`condition_on_previous_text=False`、`hallucination_silence_threshold`、
各種 `temperature`。segment 的時間戳又全是 `None`，連事後依音檔長度裁掉都做不到。

### 兩個過程中的教訓

**model card 的建議會關掉安全網。** 它說「傳 `temperature=0.0` 以求可重現」——
而那個參數平常是一串遞增值 `(0.0, 0.2, … 1.0)`：先用 0.0 解，
偵測到輸出在自我重複（compression ratio 超標）就升溫重解。
傳單一個 0.0 等於把逃生機制拆掉。**可重現與正確性在這裡是衝突的。**

**差點把自己的參數錯誤當成模型的問題。** 第一次跑出 CER 73% 時，
結論幾乎就要寫成「MLX 不行」——實際上那一輪是我關掉了退避機制。
量測工具會忠實地回報你問錯的問題。

### 結論與反悔條件

正式環境維持 CTranslate2。MLX 後端留在 `eval_asr.py` 裡，
**下次 mlx-audio 更新時一行指令就能重測**：

```bash
whisper-worker/.venv/bin/python -u eval_asr.py score \
  --backend mlx --model BRlin/Breeze-ASR-25-mlx-fp16
```

會反悔的條件很明確：**mlx-audio 修好「解到音檔長度就停」這件事**。
那之後 RTF 0.33 對 0.47 的差距就值得拿了，而且 worker 搬到宿主機
還能順便吃到 Metal——代價是重新引入決策 15 花力氣解掉的
「要記得啟動」問題，那時再用 LaunchAgent 處理。
